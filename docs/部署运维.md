# 部署运维

从零到能干活，以及出问题怎么查。

---

## 一、环境要求

| 项 | 要求 | 检查 |
|---|---|---|
| Node.js | **≥ 22.5.0**（需要 `node:sqlite`） | `node -v` |
| 操作系统 | Windows 10/11（主子机）、macOS（笔记本节点） | — |
| 磁盘 | 约 100 MB（台账 + 日志 + 报告） | — |
| 网络 | 节点能访问中台的 `http://<host>:8787` | — |

本项目**零 npm 依赖**，不需要 `npm install`，不需要 `node_modules`。

`node -v` 低于 22.5 会报 `Cannot find module 'node:sqlite'`。

### 3.2 Mac 笔记本（执行节点 B）

macOS 没有 `.cmd`，直接跑：

```bash
cd hub
node src/m3/worker.mjs --node mac-b --engines codex,mock --hub http://<Windows主机IP>:8787
```

中台默认只监听 `127.0.0.1`，要让 Mac 连进来得改 `config/hub.config.json`：

```json
"hub": { "host": "0.0.0.0", "port": 8787 }
```

改完重启中台。Windows 防火墙放行 8787 端口。

> ⚠️ 监听 `0.0.0.0` 意味着同网段任何机器都能访问。至少要改 `hub.secret`（见 §4.1）。

### 3.3 已部署为 Windows 服务（2026-11-14 落地）

本机已经注册了两个计划任务，**登录自动启动 + 崩溃自动拉起**，无需管理员权限：

| 任务名 | 作用 |
|---|---|
| `AgentsWorkflow-Hub` | 中台 `src/index.mjs`（端口固定 127.0.0.1:8787） |
| `AgentsWorkflow-Worker-win-a` | 执行节点 win-a，引擎 `claude-code,codex,mock` |

实现方式（都不需要管理员）：

- 计划任务用 `schtasks /create /xml` 注册（登录触发、InteractiveToken、无时限、失败重启）。
- 每个任务的动作是 `wscript.exe` 跑 `scripts\service\start-hub.vbs` / `start-worker.vbs`：隐藏窗口，内部是个监督循环 —— node 崩溃退出后 5 秒自动重启，干净退出（exit 0）才收工。
- 已实测：杀掉中台进程，12 秒内自动恢复，任务照常执行。

日常命令（都在 `hub\scripts\service\`）：

```cmd
scripts\service\start-all.cmd   :: 立即启动两个任务（不等下次登录）
scripts\service\stop-all.cmd    :: 全部停掉（先杀监督脚本再杀 node）
schtasks /query /tn "AgentsWorkflow-Hub" /v   :: 看任务状态
```

开机顺序：两个任务登录时同时触发，worker 连不上中台会自己重试，无依赖问题。改完代码后 `stop-all.cmd` → `start-all.cmd` 重启。

要彻底卸载：

```cmd
schtasks /delete /tn "AgentsWorkflow-Hub" /f
schtasks /delete /tn "AgentsWorkflow-Worker-win-a" /f
```

## 四、配

改 `config/hub.config.json` 后**重启中台**生效。

改 `config/rules.json` 有两条路：

- **面板「规则」页**（推荐）：点任意一行弹出编辑器，全部选项都是下拉。保存即生效，不用重启 —— 写盘前会校验引擎是否已安装、节点是否存在、技能是否在库、cron 能不能解析，校验不过整笔拒绝，不会写坏文件。
- **手改 JSON**：也能热重载（1 秒内生效），但没有校验。手打 `github.pull_request` 少一个下划线，这条规则就会永远匹配不上而没有任何报错。改前先备份。

命令行改法同面板同一套校验：

```bash
curl -X PUT http://127.0.0.1:8787/api/rules/r01-daily-report -H "x-hub-token: <secret>" -H "content-type: application/json" -d "{\"priority\":\"P1\"}"
curl -X DELETE http://127.0.0.1:8787/api/rules/r06-manual-query -H "x-hub-token: <secret>"
```

### 4.1 访问令牌

默认 `hub.secret` 是占位值，本地单机时中台不设防。要让别的机器访问，先改掉：

```json
"hub": { "secret": "换成一串随机长字符串" }
```

之后所有请求要带令牌：

```cmd
curl -H "x-hub-token: 你的密钥" http://127.0.0.1:8787/api/health
```

或者 `?token=你的密钥`。

### 4.2 飞书（把通知和批红搬到手机）

两种接入方式，先选再配：

**单向模式（已验证，2026-11-14 接入）**：机器人把通知和批红卡**推送到**飞书，批红动作在本地面板（手机连同一 Wi-Fi 也能开面板）。不需要公网 IP，不需要事件订阅。

**双向模式（已验证，2026-11-14 接入，长连接方案）**：手机上直接点卡片按钮批红，群里发消息派任务。走**飞书官方长连接**（WebSocket）——不需要公网 IP、不需要域名证书、不需要内网穿透（曾试过 sakuraFRP 穿透回调 URL，被其自签证书卡死：SakuraFrp「自动 HTTPS」颁发的是自家 CA 的自签证书，飞书服务端不认。长连接是出站连接，整个问题不存在）。

双向比单向多三步（开放平台上操作，配置文件不变）：

1. 开放平台 → 事件与回调 → 订阅方式切换为「**使用长连接接收事件**」（切走之后回调 URL 一栏整个不需要）
2. 添加事件订阅：`im.message.receive_v1`（接收消息）
3. 创建版本并发布（权限变更要重新发布才生效）

中台侧：`feishu.enabled/appId/appSecret` 齐全时启动自动拉起长连接（`/api/health` 的 `feishu_ws` 字段显示连接状态）。连通后：

- 群里 @机器人 说「**今天的事汇总一下**」→ r14 派 codex 做快查
- 「**dev: 给 README 加部署小节**」→ r13 派 claude 进仓库写代码开 PR（`dev:` 前缀防止随手聊天误触发开发任务）
- 批红卡按钮「批/驳/改派」直接生效，按钮上会弹 toast 回执（已批红/已驳回/已转改派：标题）

双向链路的卡片回调经 `/api` 共用业务链（`index.mjs` 的 `handleFeishuCallback`），HTTP webhook 路径保留（配了 `verificationToken` 就强制验签，长连接推送的是明文事件、通道本身已鉴权，无需验签）。

单向模式五步（配套自检脚本 `scripts/feishu-setup.mjs`）：

1. [飞书开放平台](https://open.feishu.cn/) → 创建企业自建应用
2. **权限管理**：开通 `im:message:send_as_bot`（发消息）、`im:chat:read`（列群找 chat_id 用）
3. **版本管理与发布**：创建版本并发布（不发布机器人加不进群），可用范围包含自己
4. 飞书里把机器人拉进目标群：群设置 → 群机器人 → 添加机器人
5. 验证凭据并拿 chat_id，然后填配置：

```
node scripts/feishu-setup.mjs --app-id cli_xxx --app-secret yyy
  # ✓ 凭据有效 + 列出机器人所在群（chat_id 在这里）

node scripts/feishu-setup.mjs ... --chat-id oc_xxx --send-card
  # 向该群发测试消息 + 演练卡片，确认送达
```

```json
"feishu": {
  "enabled": true,
  "appId": "cli_xxxxxx",
  "appSecret": "xxxxxx",
  "chatId": "oc_xxxxxx",
  "verificationToken": "",
  "encryptKey": ""
}
```

单向模式下 `verificationToken`/`encryptKey` 留空是安全的：中台绑 `127.0.0.1`，回调根本进不来，没有可伪造的入口（doctor 会显示「单向模式：暂无风险」）。但只要把 `hub.host` 改成对外地址，必须立刻配密钥，否则 doctor 判死。

批红卡（文本形态）会带上批红入口指引（面板地址 + CLI 命令）。没配飞书也能跑：通知降级到 `channel: 'local'`，也就是面板 + 控制台输出。

> **接飞书时踩过的坑（2026-11-14）**：验收时死信通知走了 `channel: 'local'` 而不是 feishu——排查发现是**上一个会话的中台进程没杀干净**（它监听 8793，清理时只杀了 8787 端口的进程）。旧进程内存里还是「飞书未启用」的旧配置，却对同一个 `hub.db` 跑着自己的 5 秒 sweep，通知全被它截走降级。**排查办法**：`Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 看所有 `src/index.mjs` 进程的启动时间——出现两个中台就是僵尸（`Get-Process | Where CommandLine` 在 PowerShell 里拿不到命令行，必须用 Get-CimInstance）。重启中台前务必确认只剩一个。

### 4.3 GitHub Webhook

```json
"github": {
  "webhookSecret": "和 GitHub 那边填一样的密钥",
  "webhookUrl": "https://你的公网入口/webhook/github",
  "allowedRepos": ["你的用户名/仓库名"]
}
```

中台面板「GitHub 仓库」页可以从当前 `gh auth login` 账号选择仓库，也可以手动输入 `owner/name` 添加或移除。添加会创建或更新仓库 webhook；移除会删除本服务管理的 webhook，并从接收白名单移除。访问 GitHub API 使用本机 GitHub CLI 凭据，页面不会读取或显示令牌。`webhookIds` 由页面自动维护。

Webhook 事件订阅：`issues`、`pull_request`、`check_suite`、`workflow_run`。创建 hook 时 GitHub 会发送 `ping`，中台只返回成功、不入账也不派活。

> 当前 SakuraFrp 自动 HTTPS 使用的证书不受系统信任。若暂不配置受信任证书，GitHub hook 的 `insecure_ssl` 会设为 `1`，即关闭证书验证；GitHub 官方不推荐此设置。`webhookSecret` 仍用于校验每次 webhook 签名。

GitHub 仓库 → Settings → Webhooks → Add webhook：
- Payload URL：`https://你的域名/webhook/github`
- Content type：`application/json`
- Secret：同 `webhookSecret`
- 事件：`Issues`、`Pull requests`、`Check suites`、`Workflow runs`

`allowedRepos` 为空时**拒绝所有仓库**。这是故意的，防止误配把任何仓库的事件都收进来。

### 4.4 M4 流水线接真仓库

```json
"pipeline": {
  "mode": "real",
  "autoStart": true,
  "releaseCommand": "把你的发布命令写这里",
  "verifyCommand": "curl -s https://你的域名/api/version",
  "expectedVersion": "v1.2.3"
}
```

- 流水线各步骤统一使用当前 `agents-workflow-hub` 项目根目录。真实模式要求在合并前配置 `releaseCommand` 和 `verifyCommand`。
- `verifyCommand` 必须输出包含 `expectedVersion` 的内容才算核实通过，否则发 P0 告警。
- 第一次接真仓库建议先 `"autoStart": false`，手工触发跑两轮看看日志，再打开。

### 4.5 调并发与重试

```json
"limits": {
  "globalMaxParallel": 3,      // 全局同时执行的任务上限
  "attempts": 2,               // 单任务默认重试次数
  "retryBackoffSeconds": 20    // 重试间隔
}
```

单条规则的并发在 `rules.json` 里改 `limits.per_key`（同一 key 串行）和 `limits.max_parallel`（该规则总量）。

### 4.6 改端口

端口**已经固定在 `config/hub.config.json`**（`hub.host: 127.0.0.1`、`hub.port: 8787`），环境变量只是临时覆盖用：

```cmd
set HUB_PORT=8899
node src\index.mjs
```

要正式换端口，按顺序改三处：

1. `config/hub.config.json` 的 `hub.port`；
2. `scripts\service\start-worker.vbs` 里的 `--hub http://127.0.0.1:8787`（服务模式的 worker 参数写死在启动器里）；
3. `scripts\service\stop-all.cmd` → `start-all.cmd` 重启。

> 顺带提醒：飞书卡片里的批红入口链接取自 `hub.host/port`，换端口后新发的卡片会自动用新地址。

## 六、排障

### 6.1 中台起不来

```
[ERROR] hub exited with code 1
```

**端口被占**：

```powershell
Get-NetTCPConnection -LocalPort 8787 -State Listen | Select-Object OwningProcess
# 拿到 PID 后
Stop-Process -Id <PID> -Force
```

或换个端口：`set HUB_PORT=8899`。

**配置解析失败**：`config/hub.config.json` 有语法错误（多逗号、少引号）。用 `node -e "JSON.parse(require('fs').readFileSync('config/hub.config.json','utf8'))"` 验证。

**Node 版本太低**：`node -v` 必须 ≥ 22.5.0。

### 6.2 节点接不到任务

按顺序查：

1. 中台活着吗？`curl http://127.0.0.1:8787/api/health`
2. 节点日志里有"执行节点启动"吗？没有就是 CLI 参数或模块路径问题。
3. 节点报 `hub 不可达`：`HUB_URL` 对不对？防火墙？
4. 任务在 `queued` 但节点不接：检查规则的 `route.node` 和节点的 `--node` 是否对得上（`any` 匹配所有），以及 `--engines` 里有没有任务要的引擎。
5. 任务状态是 `awaiting_approval`：先去批红，批了才会进队列。

```cmd
node src\cli.mjs tasks --status queued
node src\cli.mjs task tsk_xxx
```

### 6.3 任务一直 running

节点可能崩了但中台还在等。等 `lease_expires_at`（120 秒）到期，`#sweep` 会自动回收重排队。立即处理：

```cmd
node src\cli.mjs task tsk_xxx        # 看 lease 何时过期
```

日志里搜 `回收过期租约`。

### 6.4 任务失败进死信

```cmd
node src\cli.mjs tasks --status dead_letter
node src\cli.mjs task tsk_xxx        # 看 result 和 runs 里的错误
```

修好原因后重试：

```cmd
node src\cli.mjs task tsk_xxx        # 面板里也有「重试」按钮
# 或直接调接口
curl -X POST http://127.0.0.1:8787/api/tasks/tsk_xxx/retry
```

### 6.5 引擎显示不可用

```cmd
node src\cli.mjs engines
```

- `claude-code` 不可用 = 没装 CLI。装了但 PATH 里找不到，重启一次命令行窗口让 PATH 生效。
- `codex` 不可用 = `codex` 命令不在 PATH。
- `mock` / `shell` 恒可用。

引擎检查逻辑在 `src/m3/engines.mjs` 的 `whichSync()`，走的是 `where`（Windows）/ `which`（POSIX）。

### 6.6 中文乱码

PowerShell 里：

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
Get-Content data\logs\hub.log -Encoding utf8 -Tail 20
```

`.cmd` 脚本一律 `chcp 65001 >nul` 开头。

### 6.7 改了代码没生效

- 面板改了 `.js`/`.css`：强制刷新（Ctrl+F5）。静态资源已经设成 `no-cache`，正常刷新就够。
- 中台改了 `src/` 下的代码：**必须重启中台**，没有热重载。
- 改了 `config/*.json`：必须重启中台。
- 改了 `skills/*/SKILL.md`：**不用重启**，每次派活现读。

### 6.8 飞书收不到消息

1. `config/hub.config.json` 里 `feishu.enabled` 是 `true` 吗？
2. `appId` / `appSecret` 对吗？看日志里有没有 `获取 tenant_access_token 失败`。
3. `chatId` 对吗？机器人被拉进那个群了吗？（用 `scripts\feishu-setup.mjs --app-id ... --app-secret ...` 复测，能列群说明凭据和权限都对）
4. 权限开通了吗（`im:message`）？应用发布版本了吗（没发布机器人加不进群）？
5. **通知走了 `channel: local` 而不是 feishu，且此刻明明配了飞书** —— 查僵尸中台进程：`Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 看有没有多个 `src/index.mjs`。旧进程内存里是旧配置（飞书未启用），却共享同一个 `hub.db` 跑自己的 sweep，会把通知截走降级到本地（2026-11-14 验收时真实踩到）。杀掉多余的，只留一个。
6. 都查完了还不行 —— 看 `node src\cli.mjs status` 的通知列表，`channel: local` 说明在走本地兜底，消息没丢，只是没发出去。

## 七、备份与恢复

### 7.1 备份

要备份的就三样：

```
data/hub.db          ← 台账（最重要）
data/reports/        ← 报告归档
config/              ← 配置、规则、决定记忆底稿
```

SQLite 单文件，直接复制即可。**建议先停中台再复制**，或者用 SQLite 官方的在线备份（不用停服务，也不会拿到写了一半的库）：

```cmd
node scripts\backup.mjs
```

或直接用包装脚本（推荐，Windows 任务计划里就指它）：

```cmd
scripts\backup.cmd                 :: 备份到 data\backups\，保留最近 30 份
scripts\backup.cmd --keep 14       :: 只保留 14 份
scripts\backup.cmd --out D:\bak    :: 备份到别处
```

它做三件事：`VACUUM INTO` 出快照 → **重新打开备份验证表结构与行数**（只检查「文件存在且大于 0 字节」不算验证，空库也满足）→ 连同 `data\reports\` 一起备（台账里 report_id 指向它，单备份 db 会留下断链）。

注册成每日任务：

```cmd
schtasks /create /tn "AgentsWorkflow-Backup" /tr "\"D:\Agents Workflow\hub\scripts\backup.cmd\"" /sc daily /st 03:30
```

> 为什么不用文档里那行 `node -e "..."`：`VACUUM INTO` 的路径在 cmd 里要套两层引号，写错会静默失败；且目标目录不存在时 SQLite 不会自动建目录，直接报错。脚本把这些都处理掉了。

### 7.2 恢复

1. 停中台
2. 把备份的 `hub.db` 复制回 `data/hub.db`
3. 起中台

台账里存着全部历史，起来就能看到。`data/logs/` 和 `data/reports/` 是辅助，丢了不影响主流程，但报告正文会丢。

### 7.3 灾难恢复顺序

```
① 恢复 config/（配置、规则、决定记忆）
② 恢复 data/hub.db（台账）
③ 恢复 data/reports/（报告正文）
④ 起中台 → node src\cli.mjs doctor 自检
⑤ 起执行节点 → 投一条 mock 任务验证链路
```

6. `node src\cli.mjs doctor` 自检

   > 单元测试必须用 `test/*.test.mjs` 这种显式 glob，**不要写 `node --test` 或 `node --test test/`**：
   > 前者会把 `data/codex-home/plugins/` 里 codex 插件自带的测试也收集进去（那些测试依赖 react/playwright，必然报
   > `ERR_MODULE_NOT_FOUND` 而整体失败），后者在 Node 24 报 `Cannot find module 'D:\...\hub\test'`。

数据库迁移都是增量的，只加表或加列，不删数据。

## 十、安全检查清单

上线到能公网访问之前，逐条打勾：

- [ ] `hub.secret` 换成一串随机长字符串
- [ ] 对外暴露时前面套 HTTPS（Nginx / Caddy 反代）
- [ ] `github.webhookSecret` 已设置，和 GitHub 那边一致
- [ ] `github.allowedRepos` 只列你自己的仓库
- [ ] `feishu.verificationToken` / `encryptKey` 已设置
- [ ] 如果 `hub.host` 不是 `127.0.0.1`，`monitor.sharedSecret` 已设置（否则同网段任何人能伪造 P0 告警）
- [ ] `config/hub.config.json` 里没有明文密码（敏感值用环境变量）
- [ ] 执行节点专用的 API（`/api/agent/*`）不暴露给外部（中台和节点在同一内网）
- [ ] `data/` 目录权限限制为当前用户
- [ ] 定期检查 `data/logs/` 有没有异常登录尝试
