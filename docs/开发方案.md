## 0. 技术选型（§12-1）

| 维度 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js ≥ 22.5 | `node:sqlite` 从 22.5 起内置，省掉一切数据库驱动依赖 |
| 数据库 | SQLite（`node:sqlite` 的 `DatabaseSync`） | 单机、单进程、事务可靠、文件即备份 |
| HTTP | `node:http` 手写路由 | 无需 Express；路由表只有 30 多条，`Router` 类 60 行就够 |
| 前端 | 原生 DOM + `fetch` | 无构建步骤、无 node_modules、改完刷新即生效 |
| 依赖 | **0 个 npm 依赖** | 断网可用、十年后还能跑、审计零负担 |
| 进程模型 | 中台进程 + N 个执行节点进程 | 节点主动长轮询，中台不需要知道节点在哪 |

**为什么不用 Express / Fastify**：这套系统的复杂度不在 HTTP 层，而在调度语义（去重、租约、状态机、幂等）。引框架只会让"读代码要跳三层 node_modules"。手写 `Router` 支持 `:param` 和 `*`，够用且一眼看穿。

**为什么不用 Postgres**：单机 7×24、日事件量在千级，SQLite 完全够；且 `hub.db` 单文件直接 `copy` 就是完整备份。

## 1. 事件信封与统一契约（§12-2 相关）

所有入口（飞书、Webhook、cron、面板、CLI）都收敛成同一个信封，定义在 `src/lib/envelope.mjs`：

```js
{
  source: 'feishu' | 'github' | 'cron' | 'web' | 'cli' | 'monitor',
  type:   'github.issue',
  target: 'owner/repo',
  summary:'修一下登录页白屏',
  link:   'https://...',
  dedupe_key: 'github.issue#owner/repo#12',
  priority: 'P0' | 'P1' | 'P2' | 'P3',
  created_at: ISO8601,
  payload: { ... }
}
```

关键函数：
- `makeEnvelope(input)` — 归一化 source 别名（`lark→feishu`、`timer→cron`、`gh→github`、`panel→web`）、priority 兜底 `P2`、缺 `dedupe_key` 时自动拼 `<type>#<target>`。
- `validateEnvelope(env)` — **返回错误数组而不是抛异常**，调用方决定怎么处理（HTTP 层回 400，cron 层记日志跳过）。
- `normalizePriority` — 非法值静默兜底到 `P2`，绝不因为一个字段写错就丢事件。

去重窗口在 `config.ledger.dedupeWindowSeconds`（默认 300 秒）：同 `dedupe_key` 在窗口内重复进来，事件状态置 `duplicate` 并记 `duplicate_of`，**不建任务**。

## 2. 规则引擎（§12-2）

`src/lib/rules.mjs`，配置在 `config/rules.json`。

### 匹配语义

规则按 `order` 升序匹配，**第一条命中即用**。匹配维度：

```json
{
  "match": {
    "source": "feishu|github|cron|web|cli|*",
    "type":   "github.issue|github.*|*|/^github\\./",
    "target": "owner/repo|*",
    "payload": { "kind": "dev" }
  }
}
```

- 字符串支持三种写法：精确、`*`（全通配）、`github.*`（前缀通配）。
- `/pattern/` 形式的字符串按正则处理。
- `payload` 是**精确键值匹配**（所有键都要对上），用于区分 `cmd.manual` 的 `kind: dev` 与 `kind: query`。

### 规则字段全表

| 字段 | 含义 | 默认 |
|---|---|---|
| `id` | 规则编号，写进台账 | 必填 |
| `order` | 匹配优先级，小的先 | 数组下标 |
| `title` | 人话标题 | `id` |
| `match` | 匹配条件 | 必填 |
| `action` | `dispatch`（派活）/ `notify`（不派活直接推人） | `dispatch` |
| `route.node` | 目标节点，`any` 表示任意 | `any` |
| `route.engine` | 引擎 id | `mock` |
| `route.model` | 模型名（透传给引擎 CLI） | `null` |
| `skill` | 挂哪套 SOP | `null` |
| `prompt` | 附加指令模板 | `''` |
| `limits.per_key` | 同一 `concurrency_key` 的并发上限 | `1` |
| `limits.max_parallel` | 该规则总并发上限 | `3` |
| `approval` | `true` / `always` 表示必须批红才能跑 | `false` |
| `silent` | `true` 写台账不推送 | `false` |
| `notify_level` | `action=notify` 时的推送等级 | `priority` |
| `schedule` | cron 表达式或定时器对象，供 M1 自动生成定时器 | `null` |

`action: "notify"` 的语义：**建事件 → 直接建票拟 → 按等级推人 → 不建任务**。对应方案里的 `review.stalled`（P1）和 `release.failed`（P0）。

| `r01-daily-report` | cron `30 7 * * *` | win-a / codex / terra | 否 |
| `r02-monitor-alert` | `monitor.alert` | win-a / codex / sol | 视内容 |
| `r03-github-issue` | `github.issue` | win-a / claude-code | 否 |

### 规则的可编辑性（§12-2 补充）

原本只能手改 `config/rules.json`。这样做有两个问题：手打 `github.pull_request` 少一个下划线就永远匹配不上，而且没有任何范围约束 —— 改错会写坏整个规则库（JSON 语法错 → 中台启动即崩，或静默加载成空规则集）。

现在改成三层：

1. **目录**（`src/lib/catalog.mjs`）：`GET /api/rules/catalog` 返回全部可选值 —— 8 种来源、14 种事件类型（每条标注归属来源，面板据此过滤）、P0-P3 等级、审批模式、处理方式、9 个 cron 预设、**当前已安装的引擎**、**配置里的节点**、**技能库里的技能**。面板的下拉全部来自这里，所以「能选什么」永远等于「系统真的支持什么」。
2. **校验**（`validateRule()`）：引擎必须在已安装列表里、节点必须在配置里、技能必须存在、cron 必须能解析、dispatch 规则必须有引擎。**校验失败整笔拒绝，绝不写半条坏规则**。
3. **写盘**（`RuleSet.save/create/remove`）：深合并（只覆盖表单改动的键，`route.model` 这类没在界面上出现的字段原样保留）→ 写 `.tmp` 再 `renameSync`（避免半个 JSON 把规则库搞崩）→ 立即 `reload` + 重建定时器，**无需重启**。

面板行为：规则表整行可点，弹出编辑器分三段（什么时候触发 / 派给谁 / 怎么执行）。联动关系：处理方式选 `notify` 时自动隐藏派活段；切换事件来源时事件类型候选跟着过滤；选引擎时实时提示「当前在线可接：win-a」或「此刻没有节点声明这个引擎，派出去会排队」；cron 选「自定义」才露出输入框。

```bash
# 命令行也能改（同一个校验，同一套目录）
curl -X PUT http://127.0.0.1:8787/api/rules/r01-daily-report \
  -H "x-hub-token: <secret>" -H "content-type: application/json" \
  -d '{"title":"每日战报","priority":"P1"}'
```

## 3. 八步处理链（§12-1）

`src/m2/events.mjs` 的 `EventService.ingest()`，全程在一个 SQLite 事务里，中途失败整体回滚：

```
① 接收入库   events 表插一行，状态 received
② 去重      dedupe_key 在窗口内已存在 → 状态 duplicate，记 duplicate_of，返回
③ 规则匹配   按 order 遍历规则，第一条命中即用
              - action=notify  → 建票拟 + 推人，状态 deciding，结束
              - 无规则命中      → 状态 unrouted，等人工处理
④ 约束检查   per_key / max_parallel 超限 → 状态 已去重(queued-wait)，不建任务
⑤ 派活       建 task，状态 queued 或 awaiting_approval，唤醒挂起节点
⑥ 结果回写   节点 POST /complete 或 /fail → runs 表记账 → 推进 task 状态
⑦ 通知决策   按 approvals.classify 判断是否要票拟；按 priority 决定通知等级
⑧ 记账       每条状态变更写 event_audit
```

**为什么全在一个事务里**：`②→⑤` 之间如果并发进来两个相同事件，靠事务串行化保证只有第一个建成任务。SQLite 的写锁在这里刚好是最好的并发控制。

**踩过的坑**：`action:'notify'` 分支原本在事务里直接 `await` 通知推送，事务还没提交就写 approvals 表，报 `statement has been finalized`。现改成：事务内收集 Promise 到 `pending` 数组，事务提交后再 `await Promise.allSettled(pending)`。对外接口是 `ingestAsync()`，同步版 `ingest()` 保留给不在意推送时机的调用方。

**踩过的坑（第二个，最严重）**：**任务状态与事件状态是两套值域，绝不能混用**。`#createTask()` 里原本写 `const status = needsApproval ? EVENT_STATUS.AWAITING_APPROVAL : EVENT_STATUS.ROUTED`，然后把 `'routed'` 直接写进 `tasks.status`；但 `queue.leaseNext()` 的查询是 `WHERE status = 'queued'`。结果：**所有按规则派出的任务永远躺在 `routed`，节点一个也接不走**，只有走 `#createAdhocTask`（显式写 `'queued'`）的手动任务能跑。
为什么测试没抓到：e2e 里长轮询那节用的是 `dispatchManual({engine:'mock'})`，走的是 adhoc 分支。
现在两套值域显式分开，`#createTask` 返回 `{status: eventStatus, taskStatus}`；e2e 也补了断言（规则任务必须 `status==='queued'`，且节点真能 `poll()` 接走）。
教训：**同类概念（任务/事件/票拟/通知）各有各的状态枚举，命名必须带前缀区分**（`taskStatus` / `eventStatus`），一眼看出没串。

## 4. 长轮询与租约（§12-4）

`src/m2/queue.mjs` + `src/m3/worker.mjs`。

```
节点                                   中台
 │  GET /api/agent/poll?node=win-a&engines=codex,mock&wait=50
 │ ─────────────────────────────────────────────►
 │                                     [没有活] 挂起 50 秒
 │ ◄────────────── 204 No Content ────  (或提前被 wakeAll 唤醒)
 │  POST /api/agent/tasks/:id/start
 │ ─────────────────────────────────────────────►
 │                                     task.status = running
 │  执行中每 10 秒 POST /heartbeat {extend:120}
 │  完成后 POST /complete {ok, text, ...}
```

- **中台从不主动连节点**。节点在 NAT 后面、IP 会变、随时关机，主动连是不现实的。
- `wakeAll()` 在新任务入队时立刻唤醒所有挂起的 poll，正常情况毫秒级响应，不用等满 50 秒。
- 租约 `lease_expires_at` 默认 120 秒，节点心跳续期。节点崩溃后，`#sweep` 每 5 秒扫一次，过期租约自动回收重新排队。
- 优先级 `P0 > P1 > P2 > P3`，同优先级按 `available_at` 先后。

**踩过的坑（两个，都是长轮询独有的）**：

1. `#wait()` 里的 `setTimeout` 原本被 `.unref()` 了。Node 发现事件循环里没有活跃句柄，直接退出进程——表现为"长轮询一挂起，整个节点无声无息地死了"。修法：把 timer 存进 `this.timers` Set 且不 unref，`stop()` 时统一清理。

2. **跨进程唤醒失效**（最隐蔽）。`queue.wakeAll()` 只唤醒**当前进程**里挂起的 waiter。CLI 是个独立进程，它调 `hub.dispatchManual()` 建任务时，`wakeAll()` 唤醒的是 CLI 自己那个空队列，而中台进程里 worker 挂着的长轮询完全收不到信号——任务只能等 50 秒窗口结束自然超时后才被发现。表现为"手动派活后要等 20~45 秒才被接走"，而进程内测试永远是 500ms。
   修法：CLI 的 `submit` 先探测 `/api/health`，**中台在线就走 HTTP `/api/dispatch`**，由中台进程自己建任务、自己唤醒；中台不在线才直接写本地台账（此时节点也没在轮询，不存在唤醒问题）。
   一般规律：**任何跨进程"通知"都必须是 HTTP，不能靠进程内事件**。定时器（`cron-adapter`）和 Web 面板都在中台进程内，天然没有这个问题。

## 5. 执行引擎封装与沙箱（§12-4）

`src/m3/engines.mjs`，四个引擎：

| 引擎 | 命令 | 用途 |
|---|---|---|
| `claude-code` | `claude -p <prompt> --output-format json` | 主力开发（本机未装，显示不可用） |
| `codex` | `codex exec --skip-git-repo-check --color never [--cd wd] [-m model] --sandbox <ro\|rw> <prompt>` | 运维、日报、查 bug |
| `mock` | 无（读 `payload.mock`） | 演练与自测 |
| `shell` | `payload.mock.command` | 本机脚本（仅 win32） |

统一签名：

```js
runWithEngine({ engineId, prompt, task, workdir, model, mode, log, logDir })
  → { ok, exitCode, text, error, durationMs, logPath, engine }
```

- `mode: 'review'` / `'readonly'` 时自动降权：claude 加 `--permission-mode plan`，codex 用 `--sandbox read-only`。
- 每次执行落一份完整日志到 `data/logs/`，路径记进 `runs.log_path`。
- 超时统一 `code=124`（与 shell 约定一致），节点据此判断是否可重试：`exitCode !== 126 && exitCode !== 403` 才重试。
- 提示词由 `src/m6/skills.mjs` 的 `buildPrompt()` 拼装：任务 → 事件参数 → 已定过的事 → 执行 SOP → 额外指令 → 输出要求。

### Windows 上跑外部 CLI 的三个坑（都得踩一次）

1. **`.cmd` / `.bat` 不能裸 spawn**。Node 20.12+/18.20+ 为修 CVE-2024-27980，禁止无 shell 执行批处理，`spawn('codex.cmd', args, {shell:false})` 直接抛 **`spawn EINVAL`**。
2. **走 cmd.exe 会让中文乱码**。套 `cmd.exe /c` 后命令行经过代码页转换，含中文的提示词传给 codex 会坏掉（英文正常）。修法不是改代码页，而是**把 npm 的 `.cmd` shim 解析成 `node + <entry>.js`**（npm 生成的 shim 永远是 `"%_prog%" "<entry>.js" %*` 的形状），直接起 `process.execPath`。见 `resolveNpmShim()`。这一步顺带解决了引号问题。
3. **CLI 可能永不退出**。`codex exec` 会加载 `~/.codex/config.toml`，桌面版配置里常挂着 `mcp_servers.node_repl`（常驻子进程）和 `notify` 钩子（指向 Codex Desktop exe）。turn 跑完后这两者不释放，进程挂到超时——但**输出其实早已写完**，非常容易误判成"模型没响应"。
   修法：加 `--ignore-user-config`（不加载用户 config，auth 仍走 `CODEX_HOME`）。
   另外 `stdio` 的 stdin 必须显式 `'ignore'`，否则默认 pipe 永不关闭，CLI 打印 `Reading additional input from stdin...` 并等 EOF。

只影响 Windows + npm 全局装的 CLI；`claude` 走同样的 shim 路径，一并受益。

## 6. M4 五步流水线（§12-5）

`src/m4/pipeline.mjs`。

```
① 审查  reviewerEngine(主引擎)  ← 换引擎审，claude 写的让 codex 审
        最多 3 轮，第 3 轮不过 → 停止并建 P1 票拟（review.stalled）
        要求输出含「结论：通过」
② 检查  typecheck / test / build 全绿（命令可配）
③ 合并  gh pr merge <n> --repo <repo> --squash --delete-branch
④ 发布  config.pipeline.releaseCommand
⑤ 核实  跑 verifyCommand，stdout 必须含 expectedVersion
        对不上 → P0 票拟（release.failed）
```

- `mode: "mock"` 时五步全模拟，用于演练与自测；`"real"` 真跑；`"auto"` 有 git 就走真实步骤。
- `autoStart: false` 时不自动触发（默认值，避免误跑真仓库）。此时**手动入口有三个**：面板「流水线」页的触发表单、`POST /api/pipeline`、`hub.pipeline.run()`。
- 每步都写 `pipeline_runs` 一行，`seq` 自增主键。**坑**：原先拿 `pipeline_id` 当主键，第二步就撞 `UNIQUE constraint`；现在一次流水线五行，靠 `seq` 区分。
- `run()` 返回 `{ ok, pipeline_id, steps: [{step,label,ok,skipped,durationMs,error,warning}], skipped_steps, dry }`，五步齐全，面板直接渲染。

### 6.1 七个踩过的坑（都会让「通过」变成假象）

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| `hasGit()` 恒 false | 五步永远走模拟，连"合并不存在的仓库"都返回成功 | 写了 `require('node:child_process')`，纯 ESM 里 `require` 不存在 → 抛异常 → 被 catch 成 false | 改用 `spawnSync('git.exe', ['--version'])` 真探测；`dry` 暴露到 `/api/pipeline` 与面板横幅 |
| 审查换不出引擎就拿 mock 顶 | 一次审查没做，却报「连续 3 轮未通过」推给人 | `#reviewerEngine` 换不出时回退 mock，而 mock 输出不含「结论：通过」→ 稳定失败 3 轮 | 换不出就返回 null，①标记 `skipped` 并如实告警，绝不用 mock 冒充 |
| 步骤状态落库错乱 | 同一条流水线里 review 显示「完成」，其余显示 `passed` | 每次 `#record` 都新插一行，`running` 行永不关闭，收尾批量 `UPDATE ... status='completed'` 全改成完成 | `running` 插一行记住 seq，终态回头更新那一行；一步一行 |
| `runProcess` 经 cmd.exe 丢 stdout | ④⑤无论期望什么版本都报「线上版本不含预期标记」 | `windowsVerbatimArguments` 只按 `.cmd/.bat` 判断，cmd.exe 本身不算 batch → Node 二次转义 → 命令行指向不存在的程序 | `viaCmd = isBatch \|\| /(^\|[\\/])cmd(\.exe)?$/i.test(spawnBin)`；cmd 路径**原样传 args**，不再 join |
| 模拟模式却说「已上线」 | 演练跑完推 P1「五步全部通过，已上线」 | 通知文案没区分 dry | dry 时降 P3 归档，文案改「演练完成（未真合并、未真发布）」；失败分支同理降级改口径 |
| **npm shim 双形状 / cmd.exe 截断多行** | 审查连续 3 轮「不通过」，模型每次回「你只给了角色设定，没有具体任务」——**看起来像模型不配合，实际是提示词被砍掉了** | `claude.cmd` 的 shim 指向 `.exe`（`"%dp0%\...\claude.exe" %*`），而 `resolveNpmShim` 只认 `"%_prog%" "<entry>.js"` 的 node 形状 → 解析失败 → 落到 `cmd.exe /c` 分支 → **cmd 把参数里的换行当命令分隔符**，多行提示词静默截断成第一行 | `resolveNpmShim` 同时认 `.js` 与 `.exe` 两种 shim；`viaCmd` 加 `!shim` 守卫；真要走 cmd 时遇到含换行的参数**显式报错**而不是静默截断 |
| **`claude -p` 不带 permission-mode** | 任务 `completed` + `exit_code 0`，输出里却写着「做不了：所有写操作 requires approval」，实际一行都没改 | headless 模式下任何需要批准的工具调用都被自动拒绝，而无人可批准。不显式给 `--permission-mode bypassPermissions`，这个引擎在非交互场景下完全没有动手能力 | 干活模式显式 `bypassPermissions`；审查/只读模式 `plan`（只读，且不能顺手带上干活权限）。已用两条断言钉住 |

> 最后两个坑的共同点：**症状都伪装成「模型不听话」**。看到模型说「我做不到」时，先怀疑传参和权限，再怀疑模型。

### 6.1.1 另外两个「不报错但等于没做」的坑

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **任务永远排队，没人接也没人报** | 派 `{node:'mac-b', engine:'codex'}` 而 mac-b 只声明了 `mock` —— 任务永远停在 `queued`，面板上看着像「还没轮到」，实际已死锁 | 队列只按「节点是否在线」筛任务，从不检查「在线节点的引擎集合 ∩ 任务要求的引擎」是否非空 | 新增 `#sweepStarved()`：`queued` 超过 `limits.starvedSeconds`（默认 180s）且找不到能执行的在线节点 → P1 告警，写清「谁在线、为什么不匹配、怎么处理」。**只告警不改状态**，任务仍是 queued，人改完配置它自己就能跑；同一任务只告一次，不刷屏 |
| **config 文件带 BOM 导致启动即崩** | `配置文件解析失败：... Unexpected token '﻿', "﻿{..."`，报错里看不出是 BOM | Windows 上用 PowerShell `Set-Content -Encoding utf8`（PS 5.x）存盘会写 U+FEFF；`JSON.parse` 直接拒绝 | `loadConfig` 与 `RuleSet.reload` 都在 `JSON.parse` 前 `.replace(/^\uFEFF/, '')`。规则文件那条更隐蔽：解析失败不崩，但会静默用空规则库 |

**饥饿检测为什么必须存在**：方案 §M5 铁律是「一切留痕」，但留痕 ≠ 有告警。心跳停了、租约过期会回收（有日志），可「任务根本没有节点能接」这种情况既不超时也不失败，只会一直排队。没有这条检测，人会以为系统在忙，实际是被一个拼错的引擎名卡住了。

### 6.1.2 面板上的「在线节点」为什么是必需的一列

引擎表原来只显示「装没装」。但「codex 装好了」和「此刻有节点在跑 codex」是两件事：装好了但节点没起，派出去的任务只会排队到饥饿告警。所以引擎表补了「在线的执行节点」列（没节点能跑时显示橙色 `没有节点能跑`），下面再加一块「在线的执行节点」表（节点 / 状态 / 声明的引擎 / 最近露面秒数）。

数据来自 `queue.listNodes()`（依据 `noteNode()` 在每次 `poll` 与 `heartbeat` 时刷新，90 秒不露面算离线，因为长轮询窗口是 50 秒）。

### 七类必问（白名单，只有这些能推到人面前）

| 分类 id | 中文 | 命中示例 |
|---|---|---|
| `delete_data` | 删数据 | 删除旧测试表、清理三个月前的测试数据、drop table |
| `stop_service` | 停服 | 停掉相关服务、docker stop、systemctl stop |
| `spend_money` | 花钱 | 付费、购买、升级套餐、$50 |
| `outbound_message` | 对外发消息 | 给所有用户发通知、发邮件给客户、发推特 |
| `product_direction` | 改产品方向 | 调整产品方向、砍掉功能、改商业模式 |
| `secret_rotate` | 新建或轮换密钥 | 轮换 API 密钥、.env、换 ssh key |
| `permissions` | 修改权限 | 修改权限、chmod、提权 |

判定是**两层**：
1. 配置里的 `keywords` 精确词（`config.hub.config.json` 的 `approvals.categories`），配合 `KEYWORD_SYNONYMS` 同义扩展。
2. `SEMANTIC_RULES` 意图正则兜底——口语很难穷举，靠正则兜住"意思到了"的说法。

**中文匹配的关键教训**：最早写成 `(删除|清空)\s*(表|数据)`，"清理三个月前的测试数据"匹配不上——中文会在动词和名词之间塞修饰语。改成 `动词[^。；\n]{0,14}名词` 后覆盖住了。另外中文语序两种都常见："发邮件给客户"（动词在前）和"给所有用户发通知"（对象在前），必须**两种语序都写**。

**英文要词边界**：`token` 不能命中 `tokenizer`，所以纯英文关键词走 `(^|[^a-z0-9_])kw([^a-z0-9_]|$)` 而不是 `includes`。

**第三条判据：排除否定语境（提到 ≠ 要做）**

上面两条只看"有没有出现某个词"，但真实文本里大量出现的是**描述**而不是**要做**。实测踩到过：三份日报分别写着

- 「本次未修改权限，业务待批红数量未知」
- 「被策略拒绝，未删除任何数据」
- 「2条历史日报记录被标记为权限类，需人工核查」

前两条被判成「修改权限」「删数据」，第三条也被判成「修改权限」——**一次业务动作都没有，却推了三张卡片让人批红**。白名单的意义就是"只有这些能打扰人"，被自己的文案淹没就废了。

修法两条：

1. `negatedBefore(hay, index)`：关键词左侧 8 字符窗口内出现否定词（`未 / 没 / 没有 / 不 / 不会 / 不得 / 无需 / 勿 / 别 / 禁止 / 避免 / 暂不 / 尚未 / 并非`）就算否定。`matchKeyword` 与 `semanticHit` 都过这一层——语义正则原来用 `.some(re.test)`，只看命中不看语境，改成带 `g` 副本逐个匹配拿到 `m.index` 再判。
2. `KEYWORD_SYNONYMS` 只收**动作短语**，不能只收名词。原来写 `修改权限: ['权限','授权','提权']`，于是「权限受限」「权限类」全中。改成 `['改权限','修改权限','变更权限','授予权限','赋予权限','调整权限','提权','chmod']`。密钥类同理：`['轮换密钥','新建密钥','重置密钥','密钥轮换','apikey','api key','token 轮换','改密码']`。

> 带修饰语的说法（「轮换一下 API 密钥」）仍然靠 `SEMANTIC_RULES` 的 `动词[^。；\n]{0,14}名词` 兜住，所以**判据要按 `classify()` 整体测**，只测 `matchKeyword` 会漏掉这一路。

回归结果：11 条正例全命中（含「清理三个月前的测试数据」「轮换一下 API 密钥」「给所有用户发通知」），11 条反例全不误报（含上面三条真实误判文本）。`test/lib.test.mjs` 的 `classify 端到端` 一组就是这张表。

### 票拟状态机

```
pending ──批──► approved ──► executing ──► executed ──► (完)
   │                └──────► executed
   ├──驳────────► rejected ──► revising ──┐
   └──改派──────► revising ───────────────┴──► pending
   └──超时──────► expired ──► approved / rejected
```

- `revising` 走 `resubmit()` 回到 `pending`，`revision` 计数 +1，超过 `maxRevisions`（3）不再允许改派。
- 超过 `reminderHours`（24 小时）未批：**只提醒一次**，状态不变，`reminded_at` 记账。
- **绝不默认同意**：`expired` 状态需要人显式批或驳，没有任何自动放行路径。
- 批红 → 任务回 `queued` 并 `wakeAll()`；驳回 → 任务置 `rejected` 且**写进决定记忆的"定了不做"**；改派 → 写进"定过的事"。

#### 8.1.1 票拟的三条接线缺陷（2026-11-14 实测踩到）

| 坑 | 现象 | 根因与修法 |
|---|---|---|
| `approval:'always'` 只停任务、不建票拟 | 周日大扫除（r09-cleanup）派出后任务停在 `awaiting_approval`，`tasks.approval_id` 为 **null** —— 没有卡片、没人能批、任务永久卡死，`#sweepStarved` 也不认（任务不是 queued） | `#createTask` 判出 needsApproval 后，建票拟这步**从来没人做**。修法：新增 `events.onApprovalRequired` 钩子，照 `onNotify` 的规矩把建票拟放到事务提交后（票拟要异步通知），由 Hub 建单并回填 `tasks.approval_id` |
| 已批的任务被挡住第二张票拟 | 大扫除进场时的票拟（准跑）批准后，产出里提出「将删除：本地分支…」这类**新动作**不再触发 `#maybeEscalate` | 旧守卫 `SELECT approval_id FROM approvals WHERE task_id=?` 只要有过票拟就跳过。修法：只查**还在拦着的** `status IN ('pending','approved','executing')` —— 跑之前那张已 approved 不再拦截，产出里新的必问动作有自己的新票拟 |
| 批红后节点干等 50 秒 | 批完红，任务回 queued 了，但长轮询里的节点要等当前 50 秒窗口超时才拿到活 | `decide()` 的 agree 分支只改库，从不唤醒。修法：`approvals.onApproved = () => queue.wakeAll()`，由 Hub 注入 |

验证这三条的直接办法：走真实链路派一条 `cron.cleanup` —— 事件进来任务停 `awaiting_approval`、面板批红页出现卡片（分类 `delete_data`）、批完后节点 12 秒内接单开跑。e2e §5 末尾的 7 条回归断言钉住了整条链。

### 飞书回调验签：批红的唯一防线

`POST /webhook/feishu` 是**唯一能改票拟状态的外部入口**。它一放行，任何人只要知道回调地址就能伪造一张 `approval:agree` 卡片把待批事项批掉——比系统跑不起来严重得多。

这一节记三个踩过的坑，都是"看起来能用、实际完全没设防"的那种：

| 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|
| **验签恒为 true** | 配了 `verificationToken` 也不拒绝任何请求 | `return Boolean(signature \|\| true)` 恒真；普通模式又是 `calc === signature \|\| !signature`，"没带签名"被当成通过 | 没配密钥才放行（本地语义）；配了就必须带签名且算法对得上，缺签名一律拒绝 |
| **加密模式假验签** | 带 `encryptKey` 时给任意字符串都过 | 注释写着"本地简化：只要带 encryptKey 就要求签名非空"，代码却返回常量 | 真算 `sha256(timestamp + nonce + encryptKey + body)` 比对 |
| **取错请求头，恒返回 401** | 加固验签后，用正确签名也一直 401 | 代码取 `ctx.headers.timestamp` / `.nonce`，而飞书发的是 `x-lark-request-timestamp` / `x-lark-request-nonce`，两个值恒 `undefined` | 取正确头名，并保留裸名回退 |

两个细节：

- **必须用原始请求体验签**，不能 `JSON.stringify(body)`。飞书签的是它发过来的那段字节，重新序列化会因空格、字段顺序、转义差异导致签名永不匹配。`ctx.rawBody` 就是为此留的。
- 比较用 `crypto.timingSafeEqual`，长度不等直接返回 false——避免按字节提前返回泄露签名前缀。

实测（临时配置 `verificationToken: real-token-abc`，端口 8788）：

```
无签名            → 401
伪造签名 deadbeef → 401
正确签名          → 200 {"ok":false,"error":"审批单不存在"}
```

最后一行的 200 才是对的：验签通过后进入业务逻辑，因为 `apr_fake` 确实不存在。**401 变成 200 正是"验签没挡住合法请求"的证明**。

回归断言在 `test/e2e.mjs` §14（4 条）+ `test/feishu.test.mjs`（5 条），覆盖：合法签名通过、缺签名拒绝、时间戳被换拒绝、正文被改拒绝。

### 8.0 飞书通道：单向模式（2026-11-14 已接入实测）

配置后 P0/P1 即时推送（含批红卡、战报、死信）走飞书群消息。**单向**的含义：机器人只把消息**推到**飞书，手机上不点按钮——批红仍在面板/CLI 完成（卡片文本自带批红入口指引：面板地址 + `approve/reject` 命令）。

- 不需要公网 IP、不需要事件订阅，所以 `verificationToken`/`encryptKey` 留空是安全的：回调进不来，没有可伪造的入口。doctor 对这种状态显示「单向模式：暂无风险」；**但 `hub.host` 一旦对外监听，验签密钥必须立刻配，doctor 会判死**。
- 配置与自检脚本：`scripts/feishu-setup.mjs`（验凭据 → 列群拿 chat_id → 发测试消息/演练卡）。
- 实测链路（2026-11-14）：`review.stalled` → r10 → 票拟 → **`channel=feishu status=sent`**；真实每日战报（codex 跑完）→ P1 `task_result` → feishu；死信通知 → sweep 捕获直改库的死信任务 → 各通知一次（`dead_letter_notified` 去重生效）。
- 双向模式（手机点卡片按钮批红）**已经接入（2026-11-14，长连接方案）**，见下一节。

### 8.0.1 飞书长连接：双向批红的最终方案（2026-11-14 已接入实测）

**为什么不走 webhook**：双向需要飞书服务器能回调到中台。试过 sakuraFRP 内网穿透——TLS 能握手，但证书是 `CN=SakuraFrp Automatic TLS sn.2033230`（自家 CA 自签自颁，链上唯一一张，SAN 里连域名都没有），飞书服务端不信任，报 `url invalid`。没有自有备案域名，这条路到头了。长连接是中台**主动出站**的 WebSocket，不需要公网 IP/域名/证书，且官方支持卡片回调走同一通道——正好符合「中台不暴露公网」的铁律。

**协议**（从官方 SDK 源码抠出，Go/Python/Node 三家一致，字段号以 `oapi-sdk-go ws/pbbp2.pb.go` 为准）：

1. Bootstrap：`POST https://open.feishu.cn/callback/ws/endpoint`，body `{"AppID","AppSecret"}` → `{code:0, data:{URL, ClientConfig}}`；URL 自带 `device_id`、`service_id` query 参数。
2. WS 二进制帧 = protobuf `pbbp2.Frame`：1=SeqID(varint)、2=LogID、3=Service、4=Method(0=Control/1=Data)、5=Headers(repeated {1=Key,2=Value})、8=Payload(bytes)。
3. Ping：连上立即发 + 每 PingInterval（服务端下发，默认/实测 90~120s）：`Frame{Method:0, Service:<service_id>, Headers:[{type:"ping"}]}`；pong 的 payload 可能是 ClientConfig JSON（帕斯卡字段名，单位秒），要即时更新本地定时器。读超时 = 2×pingInterval+5s（超过即断线重连）。
4. 事件帧：`Method:1`，headers `type=event|card`、`message_id`、`sum`、`seq`、`trace_id`；`sum>1` 按 message_id+seq 分片重组（TTL 5s）。
5. 响应帧：原帧回写（headers 保留、可加 `biz_rt` 毫秒），payload=`{"code":200,"data":"<base64(handler 结果 JSON)>"}`；handler 抛错 code=500。卡片动作的按钮 toast 就放在 handler 返回值 `{"toast":{"type":"info","content":"已批红"}}` 里。

**实现**：`src/m1/feishu-ws.mjs`（零依赖：手写 varint 编解码 + `globalThis.WebSocket`）。`src/index.mjs` 的 `handleFeishuCallback(body)` 是 HTTP webhook 与 WS 帧共用的业务链——卡片动作 → `approvals.decide()` → 返回 toast；消息 → `ingestAsync()`。适配器抛错不外抛（返回 `{ok:false,error}`），避免飞书对不可解析消息无限重投。

**测试**：`test/feishu-ws.test.mjs` 7 项（编解码往返含中文、大 varint、ping 帧形状、响应帧 base64、分片重组、TTL）；真连接可用 `node scripts/feishu-ws-probe.mjs`（`--stay` 常驻收事件）。健康检查 `/api/health` 的 `feishu_ws` 字段实时显示连接状态。

**用户侧配置**（开放平台）：事件与回调 → 订阅方式切「使用长连接接收事件」→ 添加事件 `im.message.receive_v1` → 发布版本。回调 URL 一栏整个不再需要。

### 8.1 谁决定「要不要推」：`silent` 字段

规则里的 `silent: false` 表示「这条跑完要通知人」，`silent: true`（默认）表示「只写台账，别打扰」。

`Hub.#deliverResult(task)` 是第一句判断：

```js
if (task.meta?.silent !== false) return;   // 静默任务到此为止
```

**五个踩过的坑**（每一个都让通知"看起来配好了、实际一条没发"）：

| 坑 | 现象 | 根因 |
|---|---|---|
| `silent` 语义写反 | 07:30 战报准时跑完，一个人也没收到 | 代码 `if (task.meta?.silent !== false) { log('静默完成') }` —— 只打了一行日志，**推送分支压根不存在**。标着「不静默」的任务和静默任务行为完全一样 |
| 聚合任务自己进聚合队列（自噬） | 战报的 P2 被塞进每日聚合队列，等下一条战报带出去 → 永远等不到 | 战报本身是 P2，`Notifier.notify` 按 P2 处理。修法：`isAggregator`（skill 是 daily-report / weekly-report）时 level 强制 `P1` 走即时通道 |
| `drainDigest()` 只读内存队列 | 重启一次，攒下的 P2 全丢 | 内存数组跨进程/跨重启就没了。修法：合并 `SELECT ... WHERE channel='digest' AND status='queued'`，台账才是唯一真相；并补 `markDigestSent(ids)`，否则下发一次下次还会重复带上 |
| `dedupeRef` 收下就丢 | 同一件事反复吵人，人学会无视提醒（比不发更糟） | 形参有、函数体没用。修法：写 `notifications.meta` 后先查再发，命中返回 `channel: 'deduped'` |
| 通知只在进程内可见 | 面板上看不到任何已发/待发记录 | 没有查询接口和视图。补 `GET /api/notifications`（支持 `level`/`channel`/`status` 过滤 + `digest_queued` 计数）与面板「通知」视图 |

**为什么「聚合任务自己走即时通道」是对的**：战报是人一天里唯一一次「看总账」的机会。它自己被塞进聚合队列，等于把唯一的观察窗口丢了。

### 8.2 判据要区分「在做」和「在说」

通知发得出去之后，立刻暴露出另一个问题：战报正文里写「1项：README任务标记『花钱』…分类不一致」，系统读成「这次执行涉及花钱」，又推一张批红卡。

`negatedBefore(hay, index)` 现在有三条判据：

1. **否定词**：左侧 8 字符内出现「未/没有/不得/暂不…」——「未删除任何数据」。
2. **元话语标记**：左侧 14 字符内出现「标记/分类/归类/例如/所谓/叫做…」——「标记『花钱』」。
3. **被引号或括号包住**：`hay[index-1]` 是 `『「(【[` 之一。

第 3 条有个**陷阱**：`hay[index - 1]` 在 `index === 0` 时取到 `undefined`，而 `'任何字符串'.includes('')` 恒为 `true` —— 句首的关键词会被全部判成「被引号包住」（=在说），于是「花钱买服务器」漏判。必须先判 `prev` 非空。

这类误判的代价不对称：漏判一次是「该批的没批」，误判一次是「每天多推几张无关卡片」，人很快就不看了 —— 而白名单的价值完全依赖「推过来的一定值得看」。

### 8.2.1 第四、五条判据：名词短语与政策陈述

飞书双向打通后又暴露两类误判，根源相同：**分类器只看「这句话里有没有动作词」，不看这个词在句子里做什么成分。**

**（一）动词只是定语。** 一条回复写「端到端结果需查看飞书发送回执或群内实际消息」，`outbound_message` 的「动词 + 0~14 字 + 名词」正则命中成「发送回执或群」，于是推了一张「对外发消息」批红卡 —— 而这句话一个动作都没有。根因是正则允许中间插 14 个字符，把两个不相干的名词短语缝在了一起。

`notAnAction(hay, index, text)` 现在的判据是**窄而硬**的一条：

> 命中必须同时是「动词 + 内容名词」，**且**名词后面再没有投递目标，才算名词短语。

- 「发送回执」→ 回执后面空了 → 不是动作
- 「发送回执**给客户**」→ 有投递目标 → 是动作

第一版判据只看命中之后紧邻的那一个字是不是方位词（「群**内**」「用户**中**」），结果把真动作成批放过：`通知客户的负责人明天上线`、`通知客户等三个部门`、`通知客户所在区域的销售`、`发送报告给客户` 全部漏判。一次子代理审查把这类漏判逐条列了出来（18 条，含只差一个字的对照组：`通知客户明天上线` 命中 / `通知客户的负责人明天上线` 漏判），现在全部进了回归测试。

**教训：判据宁窄勿宽 —— 漏一张该批的卡，比多推十张无关卡片严重得多。**

**（二）政策陈述不是请求。** 模型每次回答都会复述铁律，于是回复里出现「未向飞书发送消息；对外发送需要批红。」—— 系统读成「要对外发消息」，每答一句推一张卡。这里有三个独立的洞：

1. **同义词表里又有裸词**：`对外发消息: ['对外', ...]`。这跟 §7 里「权限」那一课是同一个错误，已改成 `['对外发', '对外发送', '对外通知', '对外公布', '对外发布', '发给外部', ...]` 这样的动作短语。
2. **关键词通道绕过了所有判据**：`semanticHit` 已经在用 `negatedBefore` 和 `notAnAction` 过滤命中，但 `matchKeyword` 只调了 `negatedBefore`。两条通道必须用同一套判据，否则从关键词进来的误判一个都拦不住。
3. **回复不该走通知分层**：飞书群里问一句，产出是「回答」不是「系统主动打扰」。`notify()` 收到 `chatId` 时视为回复，P2/P3 一律即时送出、不进聚合队列、不直接归档。原先 r14 是 P3，回答被归档，人根本收不到（详见 §8.3）。

`POLICY_MARKERS`（需要批红/需审批/必须批红…）跟在命中之后时判定为陈述；但**同一句里出现 `REQUEST_MARKERS`（请批准/是否准予/同意执行/申请批准/盼批准…）就必须留卡** —— 「删除旧表需要批红，请批准」是人在申请批准，不能因为带了「需要批红」就放过。

> 这两条判据的方向是刻意不对称的：**错推**用宽判据去噪，**漏推**用窄判据兜底，谁也不许越界。

## 9. 知识资产层（§12-7/8）

### Skill 库（`src/m6/skills.mjs`）

每个 Skill 一个目录，`skills/<name>/SKILL.md`，带 front-matter：

```markdown
---
title: 每日战报
description: 汇总过去 24 小时的事件、任务与异常
tags: report,daily
engine: codex
---
正文就是 SOP，会被拼进提示词。
```

`parseFrontMatter()` 会把 `tags: a,b` 归一化成数组（**坑**：原样返回字符串时，面板 `(r.tags||[]).map` 直接崩）。8 套已就位：`daily-report`、`monitor-alert`、`repo-fix`、`repo-dev`、`quick-query`、`repo-sweep`、`weekly-report`、`cleanup`。

### 决定记忆（`src/m6/decisions.mjs`）

两种类型：
- `decided` —「定过的事」：亲口决定 + 原话 + 日期。
- `refused` —「定了不做的事」：拒绝过的事项。驳回票拟时自动写入。

底稿在 `config/decisions/seed.md`，人话格式 `- [定过的事] 内容 —— 2026-11-03`，启动时解析入库。

`relevant(query)` 给任务装配提示词用。**坑**：原先命中不够就用剩余的补齐到 8 条，导致"今天天气怎么样"也能带出 2 条不相干记忆，污染提示词。现在**只返回真正命中的**：中文按 bigram 二元组切片计分（`wordHit*3 + gramHit + tagHit*2`），过滤条件 `wordHit > 0 || gramHit >= 2`。中文没有空格，整串 `includes` 几乎匹配不上，必须走二元组。

### 事件台账 + 报告归档（`src/m6/reports.mjs`）

报告落 `data/reports/YYYY-MM/<日>-<标题>-<id6>.md`，同时进 `reports` 表。任务输出超过 400 字自动归档成报告。
