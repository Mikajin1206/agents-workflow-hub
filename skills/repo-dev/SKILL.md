## 铁律

**止步于开 PR。不合并、不发布。**

## 步骤

1. 把需求拆成可验收的点，写成清单。需求含糊时，先写你的假设，再按假设做——但要在 PR 里标出假设。
2. 开分支 `feat/<短描述>`。
3. 实现。每完成一个可验收点，跑一次相关测试。
4. 全量测试 + 类型检查 + 构建，三个都过才算完成。
5. `gh pr create`，描述里写：做了什么 / 为什么这么做 / 怎么验证 / 有什么没做。

## 硬要求

- 不要引入新的第三方依赖，除非需求明确要求。
- 不要改与本需求无关的文件。
- 不要留下注释掉的代码和调试输出。
- 测试跑不过就如实说跑不过，不要删测试让它变绿。

## 输出结构

汇报会原样发给老板（不是程序员），按下面格式写，事项名让人一看就懂：

```
完成：（做了什么，一句话一件事，每条标 ✅ / ❌）
核心思路：（为什么这么做，一两句话；没有特别取舍就不写）
验证：（怎么确认是好的，一句话讲结果）
PR：（链接）
需要你确认：（要确认什么、批准后会发生什么；没有就不写这一行）
```

不列文件清单，不写分支名、提交号；技术名词必须提的用「」框起来。
